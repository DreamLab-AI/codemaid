## Round 1 answer

**The strongest supported direction is to improve and measure review packs while testing selective upkeep in shadow mode. The evidence does not yet justify making sequence diagrams the product’s centre.** This assessment uses the supplied record; I have not audited the implementations or experiment protocols.

**1. Yes, there is a measurement mismatch—but it does not invalidate the failures.**

E0 tests upkeep efficiency. EK tests removal of diagram kinds. Neither establishes whether the corpus improves whole-system reasoning relative to other representations. However, upkeep cost remains part of the owner’s claimed value, and EK provides evidence against sequence-only review packs. Calling these experiments misaligned must not become a way to discount inconvenient results.

Run a paired evaluation using existing tools before building more:

- **A:** current narrative-plus-diagram pack.
- **B:** dense representation plus bounded source windows.
- **C:** source alone, complete where feasible.
- **D:** narrative alone, preserving A’s prose, citations and register policy.

Initially compare these as complete workflows. Then isolate representation effects by giving A, B and D identical source windows and access to follow-up tools.

Use several held-out repository snapshots and two task classes: finding defects and answering architectural/change-impact questions with checkable answers. Include naturally occurring defects whose fixes remain hidden, supplemented by realistic seeded defects. Keep the register hidden from reviewers in the primary discovery condition; test register-assisted prioritisation separately.

Blind adjudicators to the arm. Measure unique validated findings, serious misses, unsupported claims, architectural-answer correctness, and human triage minutes. Report tokens and latency alongside performance; US$8 makes API savings a weak optimisation target compared with owner attention.

Small repositories make the source-only comparison possible but remove the corpus’s claimed scale advantage. Add a large-repository condition with equal context ceilings and comparable retrieval opportunities.

The decision metric should be **useful, validated review outcomes per owner-hour**, including corpus upkeep—not recall alone.

**2. Call-flow anchoring is useful evidence, but insufficient sequence-diagram upkeep.**

An unchanged ordered callee list can accompany changes to:

- Authorisation guards or tenant identifiers.
- Argument values and returned status.
- Retry, timeout, cancellation or transaction behaviour.
- Awaiting versus spawning work.
- Error propagation and branch reachability.

Conversely, extracting a helper can change the call list without changing anything the diagram communicates. Lexical call order also does not establish runtime order across branches or concurrent tasks.

Use **claim-specific dependencies**. Each anchored arrow should identify:

1. Its caller, possible callee and call site.
2. Relevant enclosing control conditions.
3. Which argument, result, error or ordering properties the label actually claims.
4. Whether it abstracts over multiple calls or helper layers.

Hash those dependencies separately. A message labelled “send request” needs less dependency coverage than “send only after permission succeeds”.

Start with conservative syntax-based fingerprints; do not promise semantic equivalence. Changes inside callees can invalidate labels without touching the call site, so retain explicit dependencies on supporting symbols where necessary. Unmodelled claims require review.

`flows check` should distinguish **supported, contradicted and unknown**, with coverage reported. “A matching call exists” supports one narrow fact; it does not validate the diagram.

Before implementation expansion, test a mutation matrix: guards, arguments, return values, ordering, asynchronous execution, helper extraction and callee behaviour. Measure detection against whether the *documented claim* changed.

**3. Use local document identities plus versioned code locators. Neither symbol IDs nor UUIDs solve the whole problem.**

Separate identity from resolution:

- Give participants and events stable, topic-local IDs.
- Attach code locators containing the symbol ID, verified commit and optional call-site fingerprint.
- Model users, services, queues and conceptual actors explicitly, without fabricated code symbols.

Your `sym:` IDs are useful readable locators. They cannot provide rename-stable identity merely by being deterministic. A UUID can preserve document identity but cannot discover which renamed function it now denotes.

On rename or move, propose rebinding using version-control changes, signature/body similarity and structural context. Automatically accept only unambiguous cases under a declared rule; otherwise report ambiguity. Never silently attach an existing claim to a merely similar symbol.

For difficult cases:

- **Closures:** enclosing symbol plus structural/content fingerprint; ambiguity after edits is legitimate.
- **Repeated calls:** distinguish individual call sites, not just caller/callee pairs.
- **Trait dispatch:** retain the declared trait method and a known candidate set, or mark the target unresolved.
- **Non-code actors:** explicit actor kind and optional contract/document reference.

I would reject a mandatory global UUID registry. I would also reject using `sym:` as the sole enduring identity of a diagram element. The hybrid supports both readable diagnostics and durable editorial references.

**4. Highest-value next work, ranked**

1. **Evaluate existing review packs.** Build the small paired evaluation and adjudication harness above. It directly tests the owner’s actual benefit and could prevent substantial investment in the wrong upkeep mechanism.

2. **Finish E0b/E0c and collect shadow-mode false-negative evidence.** Sample both flagged and unflagged topic/commit pairs, label genuine documentation changes, and record repair time. Include natural changes as well as targeted mutations.

3. **Build a minimal claim-aware sequence checker, conditional on those results.** Deliver resolution, explicit uncertainty and useful change explanations first. Add `flows draft` if drafting is a measured bottleneck.

4. **Broaden language coverage where it changes the economics.** The 86% non-Rust citation share makes Rust-only refinement a poor route to agentbox-wide upkeep improvements. Inventory the fallback languages first; an oxc adapter is valuable only if TypeScript accounts for enough of them.

Drop the generated 1:1 corpus as a maintained deliverable; retaining it as a debug view is sensible. Pause sequence-only positioning and elaborate identity migration machinery. Do not drop other diagram kinds from review packs on EK’s evidence.

The dogfooding results justify retaining inspectable extracted views. They do not establish that those views outperform other review methods.

**5. Methodological issues to resolve**

These are risks visible in the summary; some may already be addressed in the full protocols.

- **E0 measures alerts, not unnecessary work.** Fewer flagged topics could mean better precision or missed changes. Pair reduction with detection coverage and repair effort. Report absolute counts and explain aggregation: a ratio of totals and a mean of per-commit ratios answer different questions.

- **The per-file baseline may be weak.** Compare against changed-line/citation overlap and basic declaration-aware matching. Beating whole-file invalidation does not establish that the proposed complexity is worthwhile.

- **Observations are dependent.** Commits, topics and shared symbols cluster. Confidence intervals that treat topic/commit pairs as independent will be optimistic. Use repository-level reporting and temporal/block sensitivity analyses; two repositories provide limited evidence of generalisation.

- **EK does not establish non-inferiority.** The reported interval crosses the −0.05 margin. Sequence-only’s worse point estimate than random removal is concerning, but its uncertainty matters. The margin itself needs a practical justification.

- **Byte matching is an incomplete control.** Tokens, semantic content, topic coverage and broken cross-references may differ. Distinguish removing diagrams from removing entire topics that lack sequences.

- **The finding cap creates a floor.** If each of 15 findings matches one of 427 gold items, maximum recall is about 3.5%. Use precision at a fixed review budget and detection of prioritised actionable issues. Register entries—especially Open questions—are not interchangeable with discoverable defects.

- **E0b can shrink dependencies past their meaning.** An innermost statement may depend on an outer guard, earlier binding or callee contract. Include anchor failures and ambiguous relocations in results.

- **E0c changes the claim being tested.** Lower alert volume follows partly from ignoring more kinds of change. Define hidden-change rate as missed genuinely stale cases divided by all genuinely stale cases, and separately report stale cases among unflagged outputs. “≤10%” needs an uncertainty bound and severity breakdown.

Post-stamp commits avoid some temporal problems but may introduce selection bias if stamping favours easy topics. Sample unflagged cases independently. Keep E0c labelled exploratory until a held-out prospective evaluation confirms it; dated amendments alone do not remove adaptation to earlier results.

## Round 2 answer

**A. Hunk overlap is the baseline to beat.** I would expect it to improve R substantially, especially on agentbox; I would not expect it reliably to improve hidden-change recall. Those are predictions, not measured results.

Use changed lines from a **zero-context diff**, compared against the citation window at the old revision; then relocate the citation. Otherwise Git’s display context silently enlarges k. Flag deleted anchors, ambiguous relocation and file disappearance explicitly. Pure line-number movement should not flag.

| Change | Hunk overlap | Per-symbol body hashing |
|---|---|---|
| Guard changes far above cited call | Misses outside window | Catches within symbol |
| Callee behaviour changes; caller unchanged | Misses without callee citation | Also misses without callee dependency |
| Function renamed; diagram names it, citation points inside body | Can miss declaration edit | Resolution/signature checks can catch; body hash alone may not |
| Unrelated branch changes inside huge caller | Usually avoids flag | Flags |
| Formatting/comment edit near citation | Flags | Normalised-token hashing can avoid |
| Configuration changes behaviour elsewhere | Misses without configuration citation | Usually misses too |

Other over-flags include nearby logging, tests, helper extraction and behaviour-preserving rewrites. Neither proximity nor body identity establishes whether the *documented claim* changed.

On agentbox, replacing non-Rust file fallback with local overlap should remove many alerts, including some necessary ones. On Rust, body hashing covers distant same-function changes that overlap misses. Thus **expect higher R; do not assume comparable recall**. An almost-silent detector can achieve excellent R.

Choose k from an operational convention before examining staleness labels: for example, **k=5 as the primary rule**, with k=0 and k=20 reported as sensitivity checks, never selecting the winner retrospectively. Five is a heuristic, not a semantic boundary. If tuning becomes necessary, use separate development history, then freeze it for prospective commits. Prefer explicit cited ranges when available.

**The pragmatic candidate is overlap for every language, supplemented by Rust arrow fingerprints.** Combine alerts with OR: unchanged Rust call flow must not suppress an overlap alert. Supplement plain ordered-callee deltas with the minimal context below. This remains selective change detection, not a guarantee that diagrams are current.

**B. Run a six-review screening experiment on sealmap alone.** My previous proposal was too large for the immediate decision.

Question: **Does the existing corpus workflow produce enough incremental, actionable findings to justify building better review-pack tooling next?**

1. **Spend at most 20 owner-minutes selecting three historical fixes.** Walk backwards through non-merge commits and inspect regression-test additions, rather than relying only on “fix” messages. Prefer three separate episodes. The resolver/projection regressions already reported are candidates if their fixes have executable evidence.

2. **Require an inexpensive oracle.** A regression test must fail at the fix’s parent P for the relevant behavioural reason and pass after the fix. Keep the fixing diff, commit message and added test hidden from reviewers. Reject cases needing substantial test adaptation. Use the corpus that existed at P; never regenerate it with knowledge of the fix. Record defects already disclosed by its prose and exclude them from discovery scoring.

3. **Run two arms at each P, once each, in fresh sessions.**
   - **A:** existing corpus-plus-source-window pack.
   - **B:** complete first-party source and existing tests, which fit for sealmap.

   Use the same model, settings, critical-review prompt and output limit: **three ranked, actionable findings**, each with location, triggering condition and consequence. Strip register disclosures consistently. These are workflow comparisons; unequal representations are intentional.

4. **Cap owner adjudication at 30 minutes.** Merge and deduplicate findings, hide arm labels, and validate against code/tests. Then attribute outcomes back to arms. Record confirmed findings, detection of the three hidden defects, unsupported findings and triage minutes. A plausible issue without a cheap verification route remains unverified.

**Decision rule, fixed beforehand:** if A produces at least **two additional confirmed findings across two snapshots**, while detecting at least as many hidden defects as B and requiring no more total triage time, build the smallest pack improvement that removes observed owner work—such as evidence opening or finding deduplication. Otherwise, build the hunk-overlap shadow checker next and defer additional review-pack and sequence-flow features. Keep the existing corpus workflow available.

If three eligible snapshots cannot be assembled within the selection budget, stop curating and take the latter path. That is an evidence-availability decision, not evidence against corpus value.

This deliberately sets a high bar for new investment. Three snapshots cannot establish general superiority, and historical defects may already be familiar to the owner. Hidden arm labels help attribution; they do not erase that familiarity. Campaignbuilder should be the subsequent scale check only if this cheap screen warrants expansion.

**C. Start with a conservative syntactic arrow anchor, not a claim-dependency language.**

Store these fields:

| Field | Purpose |
|---|---|
| `event_id` | Stable identity within the topic |
| `caller`, `callee` | Existing symbol locators; unresolved callee allowed explicitly |
| `site` | Baseline source span plus call-expression fingerprint |
| `verified_commit` | Revision last reviewed |
| Three baseline hashes | Call, context and order, as below |

Hash normalised Rust tokens, excluding comments and whitespace:

- **Call:** the complete containing statement, including receiver, arguments, assignment, `.await` and `?`. This catches direct argument and execution-mode changes.
- **Context:** enclosing branch predicates, match patterns/guards and loop headers, plus **preceding statements in each enclosing block within the caller**. The preceding statements catch earlier bindings and early-return guards without implementing dataflow analysis.
- **Order:** the caller’s ordered call-site projection with branch/block boundaries. This detects reordering and movement between branches; report it as syntactic ordering, not proven runtime ordering.

The context prefix can be large. Accept that initially: it is a visible, conservative trade-off, and the measured alert burden can justify narrowing it later. Hashing only enclosing predicates misses common `if denied { return; }` guards.

After edits, resolve sites using symbol location, diff mapping and structural context. A changed call fingerprint is expected; it must not prevent relocation. Ambiguous repeated calls produce **unknown/review required**, never a guessed match.

Leave out automatic transitive callee dependencies, interprocedural dataflow, semantic equivalence, dynamic-dispatch proofs, concurrency analysis, label interpretation and automatic rename migration. Existing citations can explicitly cover a supporting callee when necessary.

This should catch many local guard, argument and ordering changes. It will miss unchanged-callsite changes to callee semantics, configuration and downstream return behaviour. Its promise is **“this anchored evidence changed”**, not “this arrow is true”.

### F-01 — Internal calls written `Self::foo()` are silently deleted from every projection, because `Self` sits in the PRELUDE drop-list

- Topics: DEN-01.6, EXT-04.4, EXT-01.5, EXT-04.2
- Evidence: DEN-01.6 records that "path calls whose first segment is in PRELUDE are dropped (`resolve.rs:815`)" and that "`Self` is in PRELUDE (`resolve.rs:59`)". EXT-04.4 describes the same drop rule as a std-noise policy: "Path calls to prelude names (`Some`, `Vec::new`, `drop`) never reach the policy" (`resolve.rs:811`-`835`), and `lib.rs:59`-`63` states the intent is to drop "std, prelude constructors and calls on receivers of unknown type". Joining the two: a path call whose first segment is `Self` (e.g. `Self::new()`, `Self::helper()`) is a prelude-name drop, not a std call. Dropped calls never reach the external-calls policy, so they get no `~`, no `?`, no diagnostic; call relations are aggregated from the finished flows (`resolve.rs:318`, EXT-01.5), so the edge is absent from sequence diagrams (COR-02.1), structure `uses` edges, the overview graphs, and the dense trees — where the material itself notes the symptom: "a function whose body plainly calls something shows no calls, or a private helper appears as an entry point" (DEN-01.6).
- Failure: an agent or reviewer using the corpus or `dense.txt` to reason about a type that constructs itself via `Self::new()` and dispatches via `Self::` associated functions sees a fragmenting call graph: helpers appear as un-called entry points, real internal conversations are invisible, and `stale`/seal findings are unaffected (fingerprints are text-based), so nothing ever surfaces the gap. The product's stated value — "their honesty is what an adopter is relying on" (COR-02) — fails silently on one of the most common Rust idioms.
- Confidence: high (the two facts are asserted by the material with citations; only their join — `Self::x()` therefore dropped — is inferential, but it follows directly from the cited rules)
- Marked by authors: partially — the behaviour is recorded in DEN-01.6 as a finding "the Mermaid corpus hid", but it is nowhere labelled as accepted debt or scheduled, and EXT-04.4/`lib.rs:59`-`63` still describe the drop rule as a std-only policy, which contradicts the PRELUDE membership of `Self`.

### F-02 — The seal lock has no write atomicity or concurrency control; concurrent or crashed `seal sign` corrupts or truncates the custody record

- Topics: COR-05.3, COR-05.1, COR-04.6, COR-04.1, COR-04.4
- Evidence: `seal sign` is read-modify-write of a single shared file with nothing held between read and write: lock "parsed leniently" (`main.rs:612`-`613`), entry derived (`sign.rs:99`-`146`), then "topic written only if the pointer changed it (`main.rs:631`-`632`)" followed by "lock written canonically (`main.rs:634`)" — a non-atomic two-file write whose failure window the authors themselves document ("a failure between the two writes leaves a pointer with no entry … an interrupted sign can never pass the gate", `main.rs:632`-`634`, `check.rs:383`). No file locking, temp-file-plus-rename, or compare-and-swap appears anywhere in the material; the only concurrency consideration is at the git-merge level: "two people sealing different topics touch disjoint hunks" (`lock.rs:23`-`30`, COR-04.1), which covers two humans in two clones, not two processes in one working tree. A lock truncated mid-write is not recoverable incrementally: verify reports "one LockFault and nothing else" for an unparsable lock (`check.rs:363`-`367`, COR-04.4), suppressing all classification.
- Failure: after a large refactor the runbook is "re-sign the flagged topics"; a skill or script parallelises 20 `seal sign` invocations in one checkout (or CI races a developer signing). Each process reads the same lock, and the last writer's lock — containing only its own entry — overwrites the rest: 19 pointers dangle, the gate goes red with a LockFault storm, and the previously recorded review judgements (custody record) are gone from the lock until each topic is manually re-signed. A crash during the single lock write leaves a truncated, unparsable lock with the same consequence for all topics at once.
- Confidence: medium, inferred — reasoning from the absence of any concurrency/atomicity mechanism in the material plus the libraries-are-pure/CLI-does-IO split; the code could contain an unshown file lock, though nothing hints at one
- Marked by authors: partially — the crash window is explicitly documented as an invariant (COR-05.3); concurrent writers in one working tree are never addressed.

### F-03 — The "tidying costs nothing" fingerprint guarantee breaks inside macro arguments, contradicting the README's blanket reflow claim, and no CI job re-tests it

- Topics: EXT-06, EXT-06.4, DEL-01
- Evidence: EXT-06's business section promises "tidying code costs nothing, changing it costs exactly one re-look", backed by "reflowing tokio, VisionClaw and sealmap at a 50-column width changed no id and no hash (`README.md:197`-`198`)". The same topic then concedes the mechanism where this fails: "when a macro's arguments are not ordinary expressions, its body is only normalised token by token, so a formatter rewrite inside it can still change a fingerprint" (EXT-06 intro; the macro branch in EXT-06.4, `fingerprint.rs:113`-`116`, feeds non-expression macro bodies "as written"). The determinism/CI jobs (DEL-01.1) generate and diff fresh output of sealmap itself but never re-run a reflow experiment, so the README claim is a one-time measurement, not a gate.
- Failure: rustfmt's macro-argument formatting has been expanding release over release; on a macro-heavy crate (`write!`/`format_args!`/`quote!` bodies that are not plain expression lists), a routine `cargo fmt` produces a wave of false `Behaviour` findings (COR-04's table: body-only change). Teams respond by rubber-stamping re-signs; "re-sign everything" becomes the reflex, and real `Contract` findings drown in formatting noise — eroding exactly the routing-by-cost the fingerprint split exists for (MOD-02).
- Confidence: high that the gap exists (stated by the authors); medium that it fires in production at scale, since the material gives no measurement of macro-body reflow churn (inferred)
- Marked by authors: yes — flagged in EXT-06 as "the one gap an adopter should know about"; the tension with the blanket `README.md:197`-`198` claim and the absence of any CI coverage for it is not drawn.

## Not judgeable from this material

1. Whether the CLI writes the lock and topic files atomically (temp file + rename) or in-place truncating writes — this decides whether a crash or full disk can destroy the custody record, and the IO code (`main.rs:612`-`634`) is only described, not shown.
2. Whether any file locking or single-instance guard exists around `seals.lock` — F-02 is reasoned from absence; one look at the sign path would settle it.
3. How `--since REV` and other user-controlled strings reach `git`/`tar` (`main.rs:557`-`583`) — argv array or shell string; injection safety cannot be assessed from the distillation, nor what `tar -x` does with symlinks in an archive of an untrusted revision.
4. Whether the repo pins `seals.lock` to LF (`.gitattributes` or CI check) — without it, the documented CRLF→`LockFault` canonicality trap (COR-04.2) fires for every Windows contributor using `autocrlf`, and I cannot tell if this is mitigated.
5. What `seal sign` does when the lock text is corrupt rather than merely non-canonical (does "parsed leniently" recover, fail, or silently rebuild from pointers?), and how the skill establishes reviewer identity — both determine whether F-02-style damage is recoverable and whether the gate's review claim is enforceable at all.

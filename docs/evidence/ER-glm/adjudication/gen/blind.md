## X-01

Merged from near-identical reports; each version follows.

**Files are silently dropped at load, while the corpus contract promises exactly one document per source file and a parse error still gets one**
- Evidence: MOD-03.2's flow shows files rejected for size ("extension wanted and under 2 MiB? `source.rs:175`-`177`") or encoding ("valid UTF-8? `source.rs:181`") both terminating at "skipped silently" — no diagnostic channel exists for load-stage drops; the only diagnostics are per-parse-failure ("`build` emits one diagnostic per failed file", `crates/sealmap-rust/src/resolve.rs:217`-`221`), and the model type (MOD-03.1) has no place recording omissions. Simultaneously the corpus contract is stated absolutely: "exactly one Markdown document per source file" (`crates/sealmap-corpus/src/lib.rs:7`-`53`), and the authors work hard to preserve it even for broken input — "Keeping a module symbol for a failed file keeps the 1:1 corpus contract (one document per source) true even for broken code" (`crates/sealmap-rust/src/collect.rs:57`-`59`). The guarantee is circular: "source file" silently means "file that survived load."
- Failure: a repository contains a checked-in generated Rust file over 2 MiB (bindgen output for a large C library, a generated match table, OpenAPI-generated stubs — plausible and increasingly common). It is excluded from the `SourceSet` with no warning, so it has no symbols, no document, no index entry, and nothing in `_model.json` or `_overview.md` records the gap. An agent consulting the corpus about that file concludes it does not exist; a human comparing the corpus against the tree trusts the stated 1:1 invariant; `verify` is green because everything that was loaded checks out. The incompleteness is undetectable from sealmap's own outputs.
- Reviewer confidence: high that the drop is silent and unrecorded (stated in the diagram and absent from the diagnostic path); medium on real-world frequency of >2 MiB Rust sources (frequency judgement beyond the material).

**Files are silently dropped before the model exists, contradicting the "exactly one document per source file" contract**
- Evidence: `crates/sealmap-corpus/src/lib.rs` states the contract flatly: "For every source file `S` in the codebase the corpus contains exactly one document `S.md`", and `crates/sealmap-extract/src/lib.rs` (`Diagnostic`) reinforces it: parse failures "still get a module symbol so **every file is represented**". But representation is decided earlier, in `crates/sealmap-model/src/source.rs` (`SourceSet::load_dir`), where three filters `continue` with no diagnostic: `entry.metadata()?...len() > options.max_file_bytes { continue }` (default 2 MiB), `let Ok(text) = fs::read_to_string(path) else { continue };` (non-UTF-8), and the `filter_entry` that skips `skip_dirs` — `target`, `node_modules`, `vendor`, `dist`, `build`, `out` — at *any* depth. `crates/sealmap-rust/src/lib.rs` (`load_dir`) uses these defaults. So the parse-error path the authors instrumented (module symbol + `parse_error` tag + diagnostic) has a silent upstream twin with none of that.
- Failure: a legitimate 2.5 MB module (the crate's own tests show generated-style code is real and load-bearing), a source directory literally named `build/` or `dist/`, or one non-UTF-8 file (a stray Windows-1252 comment byte) is absent from the model: no document, no fragments in `_index.json`, nothing in `_overview.md`. `sealmap verify` is green forever, because the corpus never promised the file anything. An agent planning refactors from the corpus works against a silently incomplete map, and nothing distinguishes "verified absent" from "dropped at load".
- Reviewer confidence: high

## X-02

**Multi-repo analysis silently merges distinct crates that share a crate name**
- Evidence: `crates/sealmap/src/lib.rs` (`generate_repos`) claims "Each repository's files are prefixed with its name (`api/src/lib.rs`), crates resolve across repositories" — but only *file* paths are namespaced. `crates/sealmap-rust/src/layout.rs` (`plan`/`role_in_package`) derives the crate identity solely from each repo's own `Cargo.toml` `[package] name` with no cross-repo dedup, and `crates/sealmap-rust/src/resolve.rs` (`module_sym`/`crate_package`, `crates: BTreeSet<String>`) builds ids as `ids::package("cargo", krate)` from the name alone. Two repos each containing a crate named `common` therefore produce *identical* `sym:cargo common . …` ids. `crates/sealmap-model/src/codebase.rs` (`add_symbol`) then merges them silently: "the first definition wins for scalar fields, list fields are concatenated, and the fingerprints are folded". The one guard, `crates/sealmap-corpus/src/naming.rs` (`assert_unique_idents`), cannot catch this: it only fires when two *distinct* SymbolIds map to one diagram id; here the ids are byte-identical, so `prev == id` and no panic. It also violates the documented invariant in `crates/sealmap-corpus/src/index.rs` that `FragmentEntry.id` is "Unique across the corpus" — both repos' documents emit fragments with the same id, and `Index::fragment` finds only the first.
- Failure: `sealmap generate --repo api=../api --repo core=../core` where both contain a crate `common` (or `utils`, `core` — common names): every symbol of both crates collapses into one; api's span/file/signature/flow win by path order, core's fields are concatenated (duplicate members in structure diagrams), fingerprints merge so editing repo A marks repo B's documents stale while `verify` stays green. The corpus asserts both repos share one implementation; nothing distinguishes this from a correct run.
- Reviewer confidence: high on the mechanism (all cited code is shown and complete for this path); the absence of a guard anywhere else is inferred from the shown modules.

## X-03

**The byte-identical guarantee is false in default use: the codebase name defaults to the checkout directory's name and leaks into the output**
- Evidence: DEL-01's business section claims output is "byte-identical for the same sources and options on any machine"; MOD-03 claims "the same checkout produces the same bytes on any machine"; COR-03.4 offers the whole-corpus hash "for cheap cross-machine equality" (`crates/sealmap-corpus/src/contract.rs:174`-`183`). Against that, DEL-01.3's own diagram shows the name input "codebase name: --name, else the checkout directory's name, `main.rs:159`-`161`" with the edge `NM -.->|leaks into output| BY`, and the text records that CI must pin `--name sealmap` "so the checkout directory cannot leak into the corpus" (`.github/workflows/ci.yml:25`) — i.e. the project was already bitten once and patched its own pipeline.
- Failure: a developer runs `sealmap generate -o docs/sealmap` without `--name` from a clone at `~/work/sealmap-fork` and commits the corpus; CI verifies with `--name sealmap` and reports the entire corpus Modified (name differs in the bytes), or conversely two machines/agents clone the same commit to differently named paths, generate, and get different bytes and different corpus hashes — cache keys miss, diffs show phantom drift, and "cheap cross-machine equality" reports inequality for identical sources. Every consumer of the determinism promise who has not discovered the unpinned flag gets false results with no warning.
- Reviewer confidence: high that the name leaks into output and that the default is the directory name (both stated); medium on exactly which output artefacts carry it (inferred — the material says "leaks into the corpus" without itemising).

## X-04

**A single pathological file aborts the whole process, and the isolation layer built to contain that failure class cannot catch it**
- Evidence: EXT-01's business section promises "It never fails a whole run because of one bad file: a file that does not parse, or that trips a bug, becomes a warning and a placeholder entry," then concedes in the same section: "a file nested deeply enough to exhaust even the large stack: that still ends the process, because a stack overflow cannot be caught." The containment mechanism (`catch_unwind` at `crates/sealmap-extract/src/isolate.rs:46`) was built in response to the VisionClaw stack overflow (`docs/DESIGN.md:163`), yet stack overflow is an abort, not a panic, so the guard is void for exactly the incident class it was built for. The walker's depth cap is cited as "walking stops below 1,024 levels of expression nesting, so generated code cannot overflow the collector's stack" (`crates/sealmap-rust/src/collect.rs:1078`), but the collector's stack is also consumed by syn's own recursive parse (`collect.rs:33`) and by the fingerprint canonicalisation fold (`crates/sealmap-rust/src/fingerprint.rs:55`-`129`), neither of which that cap bounds; the material itself gives the exposure arithmetic ("syn costs about 40 KiB per nesting level in a debug build", `isolate.rs:3`-`7`).
- Failure: a contributor (or an attacker who can get one commit into any repository the harness analyses) checks in a file under the 2 MiB load cap containing a few hundred thousand levels of nested generics or parens — a few hundred KB of text. Every sealmap invocation (`generate`, `verify`, `model`) aborts with no diagnostic, no placeholder, no partial output; the CI corpus gate dies; an agent-harness run dies mid-flight. The failure repeats deterministically on every retry until the file is found by hand.
- Reviewer confidence: high that the abort is uncatchable and the cap does not bound the parse/fingerprint phases (inferred — the material shows the walker cap only covers expression walking); medium on how easily 64 MiB is exhausted in release builds.

## X-05

**A stale `_model.json` is invisible to `verify`, so the CI gate passes while the authoritative artifact is wrong**
- Evidence: `crates/sealmap-corpus/src/lib.rs` sells the safety net as "`sealmap verify` in CI plus `sealmap generate` locally keeps the corpus honest", and `generate()` writes `_model.json` only conditionally: `if options.emit_model { files.insert(reserved("_model.json"), ...) }` — it is the only reserved file that can be omitted (`CorpusOptions::emit_model`, CLI `--no-model`). But `crates/sealmap-corpus/src/contract.rs` (`verify_against`) detects orphans only via `path.extension() == Some("md") && is_generated(text)`, and the expected-vs-actual loop only flags paths present in `expected.files`. A `_model.json` left over from earlier runs with `emit_model = true` is neither expected (flag now off) nor `.md` → no drift entry, and `write()` never removes it. This contradicts lib.rs's own contract language ("nothing else in the corpus claims to describe `S`") — a stale `_model.json` claims exactly that, for every `S`.
- Failure: an operator runs `sealmap generate -o docs/sealmap`, later switches to `--no-model` (or a CI job and a local script disagree on the flag). The old `_model.json` — the "full Codebase (symbols, spans, signatures, docs, relations with confidence)" that `_README.md` tells agents to trust — now describes superseded code: wrong spans, wrong relations, stale fingerprints. `sealmap verify` exits 0 on every subsequent run; the drift the tool exists to catch is exactly the drift it cannot see.
- Reviewer confidence: high

## X-01

**Seals are self-attesting: anyone with write access to the repo — including the LLM agents the gate exists to govern — can rewrite topics and mint valid seals**
- Evidence: `crates/sealmap-corpus/src/seal/lock.rs` (`TopicSeal` doc) states a seal is "the record that a reviewer checked the topic's claims against these exact symbol versions and this exact prose." `crates/sealmap-corpus/src/seal/sign.rs` (`sign`, `Signature`): `reviewer`, `model` and `date` are recorded "as given"; the only validations are non-emptiness, a `YYYY-MM-DD` shape, and that every citation resolves with fingerprints. Nothing binds the entry to an identity, an approval event, or a key; `crates/sealmap/src/main.rs` (`sign`) overwrites the prior entry on re-sign and resets `lock.generator`. The lock is an unkeyed TOML file sitting next to the topics it attests (`seal/mod.rs`: `docs/diagrams/seals.lock`). `seal/check.rs::verify` does add a `LockFault` for a non-canonical lock, so *accidental* tamper is detected — but there is no tamper *resistance*: the canonical re-serialisation of forged content is indistinguishable from an honest one.
- Failure: an agent in the harness (or any process with commit access, the normal condition for the "agent-harness owners" this tool targets) edits a topic's claims, runs `sealmap seal sign <topic> --reviewer <anyone> --model <anything>`, and commits. `verify` passes with fabricated attestation rows. The incident shape: the gate is later cited as evidence that "a reviewer confirmed X against code version H", when the record has always been mintable by the supervised role itself.
- Reviewer confidence: high on the mechanics (all shown in the code); the exploitation path is inferred from the threat model rather than demonstrated in the material.

## X-02

**`verify` silently skips unreadable or non-UTF-8 corpus files, so a corrupted document stays green forever and `write` cannot repair it**
- Evidence: The intro claims `verify_against` "classifies every difference as missing, orphaned, stale or modified" and the business prose says "it is exact." COR-03.4 shows a fourth, unclassified outcome: entries that fail "readable as UTF-8 and relative to the root? (`src/contract.rs:125`)" go to "skipped". The drift state machine (COR-03.3) has no state for unreadable files, and the convergence test `write_converges_and_is_idempotent` (`crates/sealmap-corpus/tests/contract.rs:138`) is defined over classified files only — a skipped file is never rewritten, so it is a permanent blind spot, not a transient one. The whole-corpus hash (`crates/sealmap-corpus/src/contract.rs:174`-`183`) would differ between a corrupted and a healthy checkout, but nothing compares it in the verify path shown.
- Failure: A crash or full disk during `sealmap write` truncates a generated document to invalid UTF-8; it is committed before anyone notices. From then on every `verify` run is green and every `write` run leaves it untouched, while agents and reviewers read a mangled document behind a passing gate. The one mechanism that could notice (the cross-machine corpus hash) is not consulted.
- Reviewer confidence: high on the classification gap and the non-repair consequence; the corruption trigger is an ordinary partial-write scenario, not shown in the material.

## X-03

**Multi-repository analysis silently merges two repositories that contain same-named crates into one id space**
- Evidence: ids are keyed by crate name only. `crates/sealmap-rust/src/layout.rs` (`role_in_package`) sets each file's module to `[crate_name, …]` from that file's own `Cargo.toml`, with no repository component; `crates/sealmap-rust/src/resolve.rs` (`module_sym`, `crate_package`) builds `sym:cargo <crate_name> . …`. `sealmap::load_repos` (`crates/sealmap/src/lib.rs`) only prefixes file *paths* with the repo name; the overview groups crates by top directory for display only. So repos `api` and `core`, each containing a crate named `util`, produce identical ids `sym:cargo util . …`. Consequences are visible in code: `Codebase::add_symbol` (`crates/sealmap-model/src/codebase.rs`) merges same-id symbols with "first definition wins" for scalar fields — including `file` and `flow`, so the losing repo's call flow is dropped; `Resolver`'s item table (`Slots::insert`, "first definition wins") makes one repo's items resolvable — and callable — from the other at `Confidence::Exact`; and `naming::assert_unique_idents` (`crates/sealmap-corpus/src/naming.rs`) compares `prev == id` and therefore cannot fire on this collision, by construction. Cargo forbids duplicate package names inside one workspace, so the single-workspace case that the tests cover is exactly the case where this cannot happen; the multi-repo mode (`generate_repos`, `--repo NAME=PATH`), a first-class advertised path, is where it can. The material discusses multi-repository grouping but nowhere mentions name collisions across repositories.
- Failure: adoption of `--repo api=… --repo core=…` where both contain, say, `common`, `proto`, or two generated client crates with the same name: diagrams silently attribute the merged symbols to whichever repo sorts first by path, half the merged symbol's call flows vanish, and invented cross-repo call edges appear at `Exact` confidence between unrelated code. Seals signed against that model then attach to ids that name both crates, so a rename in one repository flips seal findings for the other. `Extraction::diagnostics` stays empty; nothing reports the collision.
- Reviewer confidence: high on the mechanism (directly shown by the code); medium overall, since it requires a same-name collision to bite — that exposure estimate is inferred.

## X-04

**`write` deletes any Markdown carrying the `sealmap: ` header, including user-authored files that are not generated output**
- Evidence: The orphan rule is "each md on disk not expected and carrying the header: Orphaned" (`crates/sealmap-corpus/src/contract.rs:99-100`), and the state machine ends "Orphaned --> [*]: write deletes it and empty parents" (COR-03.3). The stated safety invariant is that `write` "deletes only Markdown files whose YAML front matter opens on the first line (`---`) and whose first key is the `sealmap: ` marker" (COR-01.2, citing `crates/sealmap-corpus/src/document.rs:10`-`12`, `document.rs:153`-`155`). But the protection criterion and the deletion criterion are the same string: nothing in the material distinguishes "generated by this tool" from "carries this header." Meanwhile COR-03's business prose claims "anything in the directory that is not a generated document is ignored" — true of verify's comparison, false of write's deletion pass, which acts on exactly the header-bearing non-generated file.
- Failure: A developer copies a generated document (e.g. `docs/sealmap/src/auth.md` → `docs/sealmap/src/auth-notes.md`) to hand-maintain an annotated variant, keeping its front matter. The next `write` — locally, or by an auto-regenerate bot — classifies it Orphaned and deletes it, along with any empty parent directories. Regeneration restores only generated files, so the user's annotations are unrecoverable. Same loss if any other tool or template in the directory adopts the documented header shape. The verify step would have flagged it (exit 1), but a write-driven flow deletes without that gate.
- Reviewer confidence: high on the mechanism (it is the material's own classification rule); the triggering scenario is inferred, since it depends on user behaviour the material does not show.

## X-05

**The byte-identical-output guarantee fails by default: the codebase name defaults to the checkout directory name and leaks into the corpus**
- Evidence: DEL-01 promises output is "byte-identical for the same sources and options on any machine, so results can be cached, diffed and compared in CI without noise." DEL-01.3 contradicts this for the default invocation: "one input, the codebase name, comes from outside the source bytes unless it is pinned", with the node "codebase name: --name, else the checkout directory's name (`main.rs:159`-`161`)" carrying an explicit "leaks into output" edge into the determinism chain; COR-03.5 extends it ("--name, else dir name, else repo names joined with plus", `main.rs:159`-`172`). The project itself was bitten and pinned `--name sealmap` in CI "so the checkout directory cannot leak into the corpus, as the rename commit records" (`ci.yml:25`). Nothing in the mechanism forces that pin on adopters. DEL-01's business prose says "There is one live caveat on the first promise" and names only the MSRV/lockfile issue — this caveat on the determinism promise is not counted there.
- Failure: An adopter generates and commits a corpus locally in a directory named `acme`; CI checks the same commit out as `repo`. `sealmap verify` without `--name` regenerates with a different embedded name, every file differs, and per COR-03.2's own decision tree (same front-matter `source_hash` → "Modified: hand edit or new generator or options") the report misattributes the difference to hand edits. The engineer's likely "fix" — regenerating in CI — commits name churn on every path change; the cross-machine hash (`contract.rs:174`-`183`) silently disagrees between any two checkout names, defeating caching and equality checks.
- Reviewer confidence: high; every step is stated in the material, and the in-tree CI pin is evidence the failure already occurred once.

## X-06

**`sealmap verify` exits 0 (gate green) when `seals.lock` and any citing topics are missing**
- Evidence: `crates/sealmap-corpus/src/seal/check.rs` (`verify`): a `lock_text` of `None` is substituted with an empty `Lock::new()`, and the canonicality check is skipped for `None`; findings arise only from lock entries and from the `topics` map. `crates/sealmap/src/main.rs` (`Ctx::load`, `read_topics`): a missing lock reads as `None`, and `read_topics` returns an **empty map without error** when the directory does not exist (`if dir.is_dir() { … }`). `Cmd::Verify` then prints the empty report and exits 0 because `report.passes()` is vacuously true; the only trace is a stderr line "0 topic(s) checked". The material's own sibling commands contradict this posture: `Cmd::SealCheck` hard-errors when the lock is missing ("… does not exist"), and `generate --check` fails closed on a missing output directory (`crates/sealmap/tests/cli.rs`, `generate_check_compares_with_a_fresh_generation`: exit 1, "—check writes nothing"). Two of three evidence-consuming paths treat absent evidence as fatal; the flagship gate treats it as success.
- Failure: CI invokes `sealmap verify` from a subdirectory (defaults are `--root .`, `--diagrams docs/diagrams`), or a merge/refactor deletes or renames `docs/diagrams/` without updating `--diagrams`, or a sparse checkout omits it. Every sealed topic silently leaves the gate, the step goes green, and merges proceed with zero seal coverage. Same outcome for a checkout where the lock is absent and no topic currently carries `sym:` citations (e.g. all ids live inside fenced blocks, which `citations` deliberately skips).
- Reviewer confidence: high (the code paths are explicit; the material shows no guard, count check, or minimum-coverage assertion anywhere on the verify path).

## X-01

Merged from near-identical reports; each version follows.

**The seal lock has no write atomicity or concurrency control; concurrent or crashed `seal sign` corrupts or truncates the custody record**
- Evidence: `seal sign` is read-modify-write of a single shared file with nothing held between read and write: lock "parsed leniently" (`main.rs:612`-`613`), entry derived (`sign.rs:99`-`146`), then "topic written only if the pointer changed it (`main.rs:631`-`632`)" followed by "lock written canonically (`main.rs:634`)" — a non-atomic two-file write whose failure window the authors themselves document ("a failure between the two writes leaves a pointer with no entry … an interrupted sign can never pass the gate", `main.rs:632`-`634`, `check.rs:383`). No file locking, temp-file-plus-rename, or compare-and-swap appears anywhere in the material; the only concurrency consideration is at the git-merge level: "two people sealing different topics touch disjoint hunks" (`lock.rs:23`-`30`, COR-04.1), which covers two humans in two clones, not two processes in one working tree. A lock truncated mid-write is not recoverable incrementally: verify reports "one LockFault and nothing else" for an unparsable lock (`check.rs:363`-`367`, COR-04.4), suppressing all classification.
- Failure: after a large refactor the runbook is "re-sign the flagged topics"; a skill or script parallelises 20 `seal sign` invocations in one checkout (or CI races a developer signing). Each process reads the same lock, and the last writer's lock — containing only its own entry — overwrites the rest: 19 pointers dangle, the gate goes red with a LockFault storm, and the previously recorded review judgements (custody record) are gone from the lock until each topic is manually re-signed. A crash during the single lock write leaves a truncated, unparsable lock with the same consequence for all topics at once.
- Reviewer confidence: medium, inferred — reasoning from the absence of any concurrency/atomicity mechanism in the material plus the libraries-are-pure/CLI-does-IO split; the code could contain an unshown file lock, though nothing hints at one

**Seal custody is non-atomic and unguarded against concurrent writers, so the sole record of a review can be silently destroyed or corrupted**
- Evidence: `crates/sealmap-corpus/src/seal/lock.rs :: Lock` docs claim safety via ordering: "Topics are keyed and written in topic-id order … so two people sealing different topics produce disjoint hunks and a merge conflict stays within one topic" — a claim about *git merges* only. The actual write path in `crates/sealmap/src/main.rs :: sign` does an unlocked read-modify-write: `Ctx::load` reads `seals.lock` once, `seal::sign` mutates the in-memory lock, then the CLI persists with two separate plain `fs::write` calls — the sealed topic file first, the lock second — with no temp-file-plus-rename, no advisory lock, no compare-and-swap against the text that was read, and no fsync. `crates/sealmap-corpus/src/seal/sign.rs :: sign` likewise returns text for the caller to persist. Nothing anywhere in the material locks or versions the lock file.
- Failure: (a) Two `seal sign` invocations overlap — two CI matrix jobs each signing their own topics, or an engineer and an agent in the same checkout. Both read the same base lock; the second writer's `fs::write` replaces the whole file, and the first topic's seal is gone. The gate does fail closed afterwards (pointer-without-entry → `Class::LockFault`), but the custody record itself is destroyed, and recovery is to re-run the mechanical derivation — which erases any distinction between the lost review and a fresh, unreviewed signature. (b) A crash or kill between the two writes in `sign` (or mid `fs::write`, which truncates before writing) leaves either a topic with a `sealed:` pointer and no lock entry, or a truncated lock. A truncated lock makes `Lock::parse` fail, so `verify` reports one `LockFault` and *every* seal in the file is unreadable; there is no repair path in the tool short of re-signing all topics with the original reviewer/model/date. The lock is the only place the `sig_hash`/`body_hash` pairs at review time are stored; the material shows no backup, journal, or atomic-write discipline around it.
- Reviewer confidence: high — the unlocked non-atomic write sequence is directly visible; the interleavings above follow mechanically from it.

## X-02

**Internal calls written `Self::foo()` are silently deleted from every projection, because `Self` sits in the PRELUDE drop-list**
- Evidence: DEN-01.6 records that "path calls whose first segment is in PRELUDE are dropped (`resolve.rs:815`)" and that "`Self` is in PRELUDE (`resolve.rs:59`)". EXT-04.4 describes the same drop rule as a std-noise policy: "Path calls to prelude names (`Some`, `Vec::new`, `drop`) never reach the policy" (`resolve.rs:811`-`835`), and `lib.rs:59`-`63` states the intent is to drop "std, prelude constructors and calls on receivers of unknown type". Joining the two: a path call whose first segment is `Self` (e.g. `Self::new()`, `Self::helper()`) is a prelude-name drop, not a std call. Dropped calls never reach the external-calls policy, so they get no `~`, no `?`, no diagnostic; call relations are aggregated from the finished flows (`resolve.rs:318`, EXT-01.5), so the edge is absent from sequence diagrams (COR-02.1), structure `uses` edges, the overview graphs, and the dense trees — where the material itself notes the symptom: "a function whose body plainly calls something shows no calls, or a private helper appears as an entry point" (DEN-01.6).
- Failure: an agent or reviewer using the corpus or `dense.txt` to reason about a type that constructs itself via `Self::new()` and dispatches via `Self::` associated functions sees a fragmenting call graph: helpers appear as un-called entry points, real internal conversations are invisible, and `stale`/seal findings are unaffected (fingerprints are text-based), so nothing ever surfaces the gap. The product's stated value — "their honesty is what an adopter is relying on" (COR-02) — fails silently on one of the most common Rust idioms.
- Reviewer confidence: high (the two facts are asserted by the material with citations; only their join — `Self::x()` therefore dropped — is inferential, but it follows directly from the cited rules)

## X-03

**The "tidying costs nothing" fingerprint guarantee breaks inside macro arguments, contradicting the README's blanket reflow claim, and no CI job re-tests it**
- Evidence: EXT-06's business section promises "tidying code costs nothing, changing it costs exactly one re-look", backed by "reflowing tokio, VisionClaw and sealmap at a 50-column width changed no id and no hash (`README.md:197`-`198`)". The same topic then concedes the mechanism where this fails: "when a macro's arguments are not ordinary expressions, its body is only normalised token by token, so a formatter rewrite inside it can still change a fingerprint" (EXT-06 intro; the macro branch in EXT-06.4, `fingerprint.rs:113`-`116`, feeds non-expression macro bodies "as written"). The determinism/CI jobs (DEL-01.1) generate and diff fresh output of sealmap itself but never re-run a reflow experiment, so the README claim is a one-time measurement, not a gate.
- Failure: rustfmt's macro-argument formatting has been expanding release over release; on a macro-heavy crate (`write!`/`format_args!`/`quote!` bodies that are not plain expression lists), a routine `cargo fmt` produces a wave of false `Behaviour` findings (COR-04's table: body-only change). Teams respond by rubber-stamping re-signs; "re-sign everything" becomes the reflex, and real `Contract` findings drown in formatting noise — eroding exactly the routing-by-cost the fingerprint split exists for (MOD-02).
- Reviewer confidence: high that the gap exists (stated by the authors); medium that it fires in production at scale, since the material gives no measurement of macro-body reflow churn (inferred)

## X-04

**Toggling `emit_model` off leaves a stale `_model.json` in the corpus that the 1:1 contract cannot see, while `generate --check` reports clean — contradicting the "every option is part of the output's identity" claim**
- Evidence: `crates/sealmap-corpus/src/lib.rs :: CorpusOptions` states: "Every option is part of the output's identity: changing one changes the documents, which `verify` reports as [`Drift::Modified`]." But `crates/sealmap-corpus/src/contract.rs :: verify_against` detects a no-longer-emitted file only as `Drift::Orphaned`, and that arm requires `path.extension() == Some("md") && is_generated(text)`. `generate()` writes `_model.json` only under `if options.emit_model` (`crates/sealmap-corpus/src/lib.rs :: generate`), and the CLI exposes it as `--no-model` (`crates/sealmap/src/main.rs :: Generate`, `opts.corpus.emit_model = !g.no_model`). A leftover `_model.json` from a previous run is: not `Missing` (it is not in `expected.files`), not `Stale`/`Modified` (not compared), and not `Orphaned` (extension is `.json`, not `.md`). `write()` deletes only report entries, so it never removes it either.
- Failure: an operator regenerates with `--no-model` (or a harness upgrade turns model emission off to save bytes). The old `.sealmap/_model.json` — documented as "the full [`Codebase`] (symbols, spans, signatures, docs, relations with confidence)" that agents read — stays on disk describing dead code, while `sealmap generate --check` exits 0 and the drift report shows nothing. Any downstream consumer that trusts `_model.json` (its documented purpose is machine consumption) acts on a model the contract was supposed to guarantee is fresh; the same-shaped hole opens for any future option-gated output file.
- Reviewer confidence: high — every step is directly visible in the shown code; the only assumption is that something reads `_model.json` in production, which its own documentation asserts.

## X-05

**A repo's contents can abort the entire sealmap process (SIGABRT), contradicting the "never fails, diagnostics only" extraction contract; the documented depth cap guards the walker, not the parser**
- Evidence: `crates/sealmap-rust/src/lib.rs :: extract` promises "Never fails: unparsable files are reported in [`Extraction::diagnostics`]", and `sealmap-extract/src/lib.rs :: Extraction` calls its diagnostics "non-fatal". But `crates/sealmap-extract/src/isolate.rs` states the catch: "A stack overflow is an abort and cannot be caught" — `map_isolated` wraps the job in `catch_unwind`, which does not catch stack overflow. The only depth control in the Rust adapter is `MAX_EXPR_DEPTH` (`crates/sealmap-rust/src/collect.rs`), applied inside `FlowWalker::expr` — i.e., *after* `syn::parse_file` has already recursively parsed the whole file in `collect_file`. The mitigation the isolate comment pins everything on ("a language adapter's own depth cap is what actually matter[s]") therefore does not cover the parse stage where the first overflow occurs. The stack is raised to a fixed 64 MiB (`COLLECT_STACK_BYTES`), while `LoadOptions::max_file_bytes` (`sealmap-model/src/source.rs`) admits files up to 2 MiB by default — a 2 MiB file of nested `Vec<Vec<…>>` or bare parentheses carries far more nesting levels than any fixed stack absorbs. The adapter's own comment measures ~40 KiB of debug-build stack per `UInt<UInt<…>>` level, i.e. roughly 1,600 levels on the 64 MiB stack; its own test (`deep_nesting_does_not_overflow`, `crates/sealmap-rust/tests/extract.rs`) tops out at 200 levels and 300-deep expressions, nowhere near the limit.
- Failure: `sealmap verify`, `pack`, or `generate` runs over a PR or an agent-authored checkout containing a machine-generated file with deep nesting (generated type towers and builder chains are exactly what the comments say motivated the big stacks). Parsing overflows the 64 MiB stack → SIGABRT → the whole sealmap invocation dies, taking the CI gate or the harness's mapping process with it — not the per-file diagnostic degradation the contract promises. Since the system's stated purpose is analysing other people's code, this is an input-driven denial of service requiring no privilege.
- Reviewer confidence: high for the contradiction and the mechanism (unbounded parse recursion vs. fixed stack ⇒ some admissible input aborts, by their own measurements). The precise threshold is inferred; I have not seen syn's internals and cannot rule out an internal depth limit in syn 2 — but nothing in this material shows one.
